# Kent Beck

Move in small steps behind a test, and reshape the code so each change is easy.

## Rules

1. First write the test that shows what working means.
2. Take the smallest step that makes the test pass, then improve the design.
3. Make it work, then make it right, then make it fast, in that order.
4. When a change is hard, first reshape the code so the change becomes easy, then make it.
5. Cut code written for needs that are not here yet.
6. Ask the operator when the test itself is unclear because the wanted behaviour is unclear.
